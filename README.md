# Learning Shop

一个用于学习后端组件的 FastAPI 单体电商 API。所有账号权限相同：都能管理商品；每个人只能操作自己的订单与发货任务。付款和发货均为**模拟操作**，不会真实扣款或寄出商品。

## 启动

需要 Docker 和 Docker Compose：

```bash
docker compose up --build
```

启动后访问 <http://localhost:8000/> 或 <http://localhost:8000/docs> 使用中文操作页面。<http://localhost:8000/api-docs> 是接口调试文档，接口分组和操作名称也已改成中文。数据库表由 Alembic 在 API 容器启动时迁移。

也可以在本机运行 Python：先启动 PostgreSQL，并设置 `DATABASE_URL`；然后执行 `pip install -e '.[test]'`、`alembic upgrade head` 和 `uvicorn app.main:app --reload`。

## 体验一遍业务流程

1. 打开中文首页，注册 `alice`，密码至少 8 位，然后登录。此项目使用 HTTP Basic 认证，便于学习；正式系统应使用 HTTPS 和合适的登录会话方案。
2. 在“商品管理”中添加商品，例如“书籍”，价格 19.99 元、库存 3 件。页面输入元，API 和数据库存分。
3. 点击该商品的“创建订单”，购买 2 件。成功后库存从 3 变为 1。
4. 在“我的订单”中点击“模拟付款”。订单变为“已付款”；后台自动发货，“我的发货任务”显示“模拟已发货”和模拟运单号。不能重复付款。
5. 再创建一个订单，点击“取消订单”，库存会归还。
6. 点击“删除订单”会从自己的列表隐藏。待付款订单会先取消并归还库存，已付款订单只隐藏记录。

商品可通过 `PATCH /products/{id}` 修改名称、价格和上下架状态，通过 `POST /products/{id}/stock-adjustments` 传 `{"delta":5}` 补货或 `{"delta":-2}` 减少可用库存。

## 组件与关键规则

| 组件 | 作用 |
| --- | --- |
| FastAPI | HTTP 接口、输入校验、自动接口文档、依赖注入 |
| PostgreSQL | 保存数据，使用条件更新和事务避免超卖、重复付款 |
| SQLAlchemy | Python 代码与数据库之间的查询和事务接口 |
| Alembic | 记录并执行表结构变更；创建业务表与发货相关表 |
| Docker Compose | 一条命令启动 API 和数据库 |

下单时先用一条带库存条件的 SQL 更新占用库存，再写订单，最后一起提交。取消和删除待付款订单时，订单状态改变与归还库存也在同一事务里。付款时，只有 `PENDING_PAYMENT` 订单能改为 `PAID`，并在同一事务里写入付款记录和发货任务；付款表和任务表分别对订单 ID 有唯一约束。

订单保留下单时的商品名、单价和总价；后续商品修改不影响历史订单。订单删除是逻辑删除，付款记录仍保留。没有自动取消超时未付款订单，所以待付款订单会持续占用库存，直到用户取消或删除。

## 付款后如何可靠发货

主流程是：付款与任务一起提交 → 后台选中待发货任务 → 生成模拟运单并保存成功状态。`app/shipping.py` 实现处理逻辑，FastAPI 启动时开启后台线程，关闭时通知线程退出。任务保存在 PostgreSQL，进程重启后继续处理。

发货只使用一张 `shipping_tasks` 表，原有四张业务表的字段保持原样：

| 表 | 保存什么、何时写入 |
| --- | --- |
| `shipping_tasks` | 付款事务创建待发货任务；后台更新尝试次数、重试时间、错误、运单和发货时间 |

任务的 `order_id` 唯一，每个订单只有一个任务。后台使用 PostgreSQL 行锁与 `SKIP LOCKED` 选中可执行任务，在同一个短事务里生成本地模拟运单、写入运单与发货时间并改为成功。中途失败会回滚，任务仍能继续处理；提交成功后已有结果，并发执行者不会重复处理。这个过程没有调用外部仓库，因此无需领取凭证或领取超时。

订单的 `PAID` 表示付款状态，发货进度单独查看：

| 任务状态 | 含义与后续处理 |
| --- | --- |
| `PENDING` | 待发货，也包含等待自动重试的任务；失败后等待 10 秒再试 |
| `SUCCEEDED` | 模拟发货成功，保存运单和时间 |
| `FAILED` | 本轮累计 5 次失败，停止自动重试；修复失败原因后可手动重试 |

失败原因会保存到任务，后台也会记录失败日志。页面只展示订单号、发货状态、模拟运单、失败原因和重试按钮；等待自动重试的任务也可以手动提前重试。手动重试重新开始一轮尝试，成功任务不能重试。

逻辑删除只影响订单列表，发货任务不会删除，后台仍会发货，用户也仍可查看和重试。迁移时为历史已付款订单一次性补齐任务，日常不再定期巡检补任务。付款接口始终在同一事务里创建任务。

相关接口要求登录并检查订单归属：

| 接口 | 用法 |
| --- | --- |
| `POST /orders/{id}/pay` | 不带请求体，模拟付款并安排后台发货 |
| `GET /shipping-tasks` | 查看自己的全部发货任务，包含已隐藏订单 |
| `GET /shipping-tasks/{id}` | 查看单个任务 |
| `POST /shipping-tasks/{id}/retry` | 不带请求体，重新安排 `FAILED` 或已有失败原因的 `PENDING` 任务 |

默认每秒轮询，页面每 3 秒刷新。`SHIPPING_WORKER_ENABLED=0` 关闭后台执行，`SHIPPING_POLL_SECONDS` 调整轮询间隔。API 容器默认开启后台，无需额外服务。

升级前先停止旧 API 与后台线程，再执行 `alembic upgrade head`，或执行 `docker compose up --build` 让新容器的启动命令自动迁移。`0002_shipping` 会为所有有付款记录的 `PAID` 订单创建任务，**包括已隐藏的历史订单**。`0003_simplify_shipping` 将任务转换到三种状态，并移除领取字段、请求编号和模拟配置；删除旧 `warehouse_shipments` 表前，把其中已有的运单与发货时间合并进任务并标为成功。已成功任务保留原运单，历史已付款订单缺失的任务一次性补齐；后台启动后处理尚未发货的任务。降级到 `0002_shipping` 会恢复旧结构并回填成功运单，已移除的领取和故障配置历史不会恢复。

当前发货只是本地模拟，没有真实仓库或物流调用。如果以后接入真实仓库，需要重新处理外部请求去重与结果查询，不能把外部调用直接放进当前数据库事务。真实支付还需验证回调、主动查单和对账；退款流程尚未实现。

## 设计怎么理解

一次请求的路径是：客户端 → FastAPI 路由 → 身份校验与参数校验 → 商品/订单业务代码 → SQLAlchemy → PostgreSQL → 返回响应。`app/schemas.py` 定义请求和响应的数据形状，`app/auth.py` 根据 HTTP Basic 凭据找到当前用户，`app/main.py` 执行业务规则，`app/models.py` 定义数据库表。这里的 FastAPI 依赖注入负责把数据库会话和当前用户传给接口；它常被口头称为“中间件”，但和包在整个 HTTP 请求外层的请求日志中间件不是一回事。

**下单最难的是并发。** 如果库存只有 1，两个请求都先读取“还有 1 件”，随后各自减 1，就可能超卖。本项目让 PostgreSQL 执行一条带 `available_stock >= quantity` 条件的更新；只有成功扣减的请求能创建订单。订单写入和库存扣减同处一个数据库事务，中途失败会一起回滚。

**取消与付款也会竞争。** 两个操作都要求订单还是 `PENDING_PAYMENT`。数据库中的条件更新让其中一个先改变状态，另一个得到 409。付款表的 `order_id` 唯一约束再提供一层保护。这些规则属于数据库和业务逻辑，换成 Go 或别的框架仍要处理。

当前是**单体架构**：一个 FastAPI 进程管理所有业务、一个 PostgreSQL 数据库保存所有数据。优点是业务路径短、部署简单、同一数据库事务易于保证库存和订单一致；缺点是以后功能变多时，必须持续维护清晰的模块边界，发布通常一起进行。

如果以后拆成商品服务、订单服务、付款服务，各自有数据库，就能分别部署和扩容，但下单会跨服务：扣库存成功、创建订单失败时要归还库存；消息或支付回调也可能重复或延迟。那时还需要跨服务补偿和监控。当前发货使用数据库任务表完成异步处理，暂时不引入 Redis、消息队列或网关。

## 开发测试

测试需要一个独立的 PostgreSQL 数据库，避免清理开发数据：

```bash
docker compose exec db psql -U shop -d shop -c 'CREATE DATABASE shop_test;'
export TEST_DATABASE_URL=postgresql+psycopg://shop:shop@localhost:5432/shop_test
pytest
```

测试会在 `shop_test` 中建表并清空测试数据。不要将 `TEST_DATABASE_URL` 指向保存重要数据的数据库。

测试默认关闭应用的后台线程，显式驱动任务执行，验证付款与任务原子提交、失败重试与上限、并发处理、发货事务回滚、隐藏订单继续发货及后台异常恢复。故障通过测试中的替代函数触发，页面不再提供故障场景选择。
